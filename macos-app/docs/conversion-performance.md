# 旧版と最終版の性能比較

品質改善前と、配置制約まで反映した最終版を、同じ条件で変換して比較する。
測るのは CLI の起動から終了までの経過時間と、そのプロセスのピーク RSS とする。
ビルド、モデルの取得、モデルのコピーとハッシュ照合、計測外の準備実行、出力検証は含めない。

## 2026-10-28 の計測結果

Apple M5 (CPU 10 コア、メモリ 32 GiB)、macOS 27.2 arm64、Rust 1.93.0、Python 3.12.12 で測った。
初回の各条件 3 回で時間に大きな幅が見られたため、同条件で 3 回ずつ追加し、各条件 6 回、合計 24 試行を集計した。
遅かった試行も除外していない。
準備実行は 2 バッチで計 4 回行い、集計から除外した。
全試行の数値とハッシュは [結果 JSON](conversion-performance-results.json) に保存した。

表は中央値 (最小〜最大) を示す。
時間の単位は秒、RSS は GiB (`1 GiB = 1,073,741,824 bytes`) とする。

| キャッシュ条件 | 版 | 時間 (秒) | ピーク RSS (GiB) |
| --- | --- | --- | --- |
| モデル変換キャッシュなし | 旧版 | 45.52 (33.61〜47.54) | 1.627 (1.625〜1.629) |
| モデル変換キャッシュなし | 最終版 | 40.15 (27.54〜40.37) | 1.672 (1.668〜1.679) |
| 準備済み | 旧版 | 43.55 (31.01〜43.94) | 1.210 (1.130〜1.225) |
| 準備済み | 最終版 | 28.54 (25.68〜38.11) | 1.335 (1.230〜1.345) |

中央値同士では、モデル変換キャッシュなしの時間は 11.8% 低下し、RSS は 45.5 MiB (2.7%) 増加した。
準備済みの時間は 34.5% 低下し、RSS は 127.6 MiB (10.3%) 増加した。
この比較は、同じ原稿と設定での観測結果である。
時間の範囲が重なり、OS のメディア解析や VM のバックグラウンド負荷も記録されたため、他の環境でも同じ速度差になると保証する結果にはしない。
演算別のプロファイルは取っておらず、個別の修正の寄与量も未測定である。

### 出力とモデルの同一性

計測した 24 回と準備実行 4 回の全出力は、それぞれの参照 PPTX とファイル全体の SHA-256 が一致した。
旧版は全 14 ページ、313 文字枠、最終版は全 14 ページ、240 文字枠を維持した。
最終版の参照は、ユーザーが確認した配置制約版 `aca8cb9a…` である。
LaMa の警告や補間へのフォールバックは検出しなかった。

元モデルは `1faef530…`、変換後の ONNX は `bc72d903…` で、変換後のハッシュは全 28 回で一致した。
外部依存は 521 パッケージで、版と取得元が両版で一致した。
各コミットの Cargo.lock は、ワークスペース内の依存宣言の差を保持したまま使用した。
入力、バイナリ、参照 PPTX、フォントの完全なハッシュは結果 JSON とローカルのマニフェストへ保存した。

### メモリ増加と品質上の利点

RSS が増えた原因候補には、背景の採色を元画像で統一するための画像保持と、行ごとの消去マスクの同時保持がある。
最終版の `prepare_text_erasure` は、複数の領域とマスクを準備してから消去する。
今回の計測だけでは、これらが増加量の何 MiB を占めるかまでは分からない。
原因を確定するには、ページ別のメモリ割り当ての追跡が必要になる。

品質上の利点は、5、12、13 ページの背景色の混入の解消、人物や画面内の細字の保護、OCR と部分強調、セルと説明枠への文字配置の改善である。
今回の最終版は、その確認済み出力を全試行で維持している。
品質改善は維持し、行ごとのマスクの保持範囲などのメモリ削減は別の調査候補として残す。
本タスクでは、性能を上げるための製品コードの変更は行っていない。

## 固定した条件

| 項目 | 条件 |
| --- | --- |
| 旧版 | `dc8230b467330002690be116aa87b3b253a8f27f` |
| 最終版 | `9d88e02fcba62007559d4742df6f59ab54de1a56` |
| 入力 | 同じ全 14 ページの PDF。SHA-256 で固定 |
| 変換 | 150 DPI、Vision `ja-JP,en-US`、自動フォント、高解像度背景 |
| 消去と画像 | LaMa、透かし除去あり、幅調整なし、物体抽出なし |
| 書き出し | 編集可能な文字、診断ファイルの保存なし |
| LaMa | 同じ元モデルを専用ディレクトリへコピー。SHA-256 で固定 |
| 実行経路 | `N2P_LAMA_DEVICE=gpu`、CoreML MLProgram の CPUAndGPU |
| プロセス | 毎回新しい CLI プロセス。同じ処理内のページ間でのモデル再利用は通常の動作を維持 |
| 回数 | キャッシュ条件ごとに各版 3 回以上 |
| 順序 | 条件の順序と、旧版と最終版の先行順を入れ替える |

各コミットから取り出したソースを、同じ Rust と release 設定でビルドする。
`--locked --offline` を使い、外部依存のパッケージ名、版、取得元が両版で一致することを確認する。
Cargo の成果物は版ごとに独立したディレクトリへ保存し、コミットを切り替えた際の古い成果物の混入を防ぐ。
バイナリ、ソースのアーカイブ、Cargo.lock、入力、モデル、参照 PPTX、使用フォントのハッシュをマニフェストへ記録する。

## 二つのキャッシュ条件

| 条件 | 計測開始前の状態 | 時間に含むもの |
| --- | --- | --- |
| モデル変換キャッシュなし (`empty`) | 元モデルだけがあり、変換済み ONNX と `coreml/v1` がない新しいディレクトリ | モデルの変換、CoreML の準備、通常の変換 |
| 準備済み (`ready`) | 版ごとの専用キャッシュで、計測外の全ページ変換を 1 回完了 | 準備済みキャッシュからの通常の変換 |

元モデルの取得時間は測らない。
既に取得した同じモデルを使い、ユーザーのモデルやキャッシュは削除しない。
`N2P_LAMA_MODEL` のパスで分離し、試行前後の生成物の一覧とハッシュを残す。

OS のファイルキャッシュ、CoreML 内部の共有キャッシュ、Vision のシステム内キャッシュは未制御である。
入力やモデルのハッシュ照合とコピーによって、ファイルの読み取りがキャッシュされる場合もある。
そのため、`empty` を「完全な cold」と呼ぶことはしない。
これは、アプリが管理する変換済みモデルと CoreML キャッシュの有無を比較する条件である。

## 計測値と出力の検証

`scripts/conversion_benchmark.py` は `wait4` のプロセス別 rusage を使う。
macOS の `ru_maxrss` は bytes、Linux/WSL2 の同じ値は KiB として扱い、保存時は bytes に統一する。
親プロセス全体の子プロセス累積値を使わないため、前の試行のメモリピークが次の試行へ混ざらない。
ユーザー時間とシステム時間、終了コード、PID、生ログも保存する。

RSS は CLI のプロセスに対する値である。
別プロセスで動く CoreML や Vision のサービスを含むシステム全体のメモリ使用量とは区別する。
GPU の経路を要求し、CoreML の生成物とログで準備の成功を確認するが、演算ごとの CPU/GPU 使用率の計測は行わない。

各出力は、版ごとに確認済みの参照 PPTX と照合する。
ページ数と文字枠数だけでなく、ZIP 内の全パーツのハッシュも比較し、文字、書式、背景画像、配置の変化を検出する。
圧縮や ZIP ヘッダーの違いは内容検証から分け、PPTX ファイル全体の SHA-256 も記録する。
LaMa の警告や補間へのフォールバック、準備済みキャッシュの欠損、変換失敗、出力の不一致があれば、その試行を成功として集計しない。
必要な回数がそろわない場合も、完成した比較結果を出力しない。

実行前後の電源状態、温度制限の情報、プロセス一覧、システムの負荷を保存する。
App Nap の設定は変更せず、新しい CLI プロセスとして起動する。
プロセスごとの App Nap 状態と、温度や周辺処理を完全には制御していないことを条件として残す。
ビルドやテストは計測と同時に実行しない。

## 再実行

Rust と `uv` を準備した環境で、リポジトリのルートから実行する。
Python の依存は標準ライブラリだけで、グローバルへパッケージをインストールしない。
`prepare` と `measure` の出力先には新しいディレクトリを指定する。
既存の結果を上書きしない。

```sh
uv run --python 3.12 macos-app/scripts/conversion_benchmark.py prepare \
  --repo . \
  --out archive/quality/performance-comparison \
  --build-target macos-app/target \
  --before dc8230b467330002690be116aa87b3b253a8f27f \
  --after 9d88e02fcba62007559d4742df6f59ab54de1a56 \
  --before-reference archive/quality/p0-background-bleed/before.pptx \
  --after-reference archive/quality/placement-constraints/after.pptx \
  --input '/path/to/source.pdf' \
  --model '/path/to/lama_fp32.onnx' \
  --font-file '/path/to/NotoSansJP[wght].ttf' \
  --repetitions 3

uv run --python 3.12 macos-app/scripts/conversion_benchmark.py measure \
  --manifest archive/quality/performance-comparison/manifest.json \
  --results archive/quality/performance-comparison/runs-01
```

同じ確定済みバイナリで再計測する場合は、`measure` の結果の保存先を `runs-02` などへ変える。
この全ページ比較は、既存の Vision と CoreML を使う macOS の条件を対象にしている。
Linux/WSL2 の CPU 実行は別の比較条件として設計し、macOS の数値と同じ標本に混ぜない。

今回と同じ 2 バッチを集計するには、各 3 回の `runs-01` と `runs-02` を作ってから次を実行する。
集計器は、マニフェスト、計測スクリプト、端末、OS が同じことと、生記録と集計値の一致を検査する。
標本の重複や条件の違うバッチを混ぜず、元ファイルのパスとプロセス一覧を公開用の JSON から除く。

```sh
uv run --python 3.12 macos-app/scripts/summarize_conversion_benchmark.py \
  --batch archive/quality/performance-comparison/runs-01 \
  --batch archive/quality/performance-comparison/runs-02 \
  --out archive/quality/performance-comparison/combined-summary.json
```

| 保存先 | 内容 |
| --- | --- |
| `manifest.json` | 固定コミット、各ファイルのハッシュ、CLI 引数、ビルド条件 |
| `build-before.log` と `build-after.log` | ビルドの生ログ |
| `binaries/` と `sources/` | 比較に使うバイナリとソース |
| `runs-01/environment.json` | 計測範囲、端末情報、制御していない条件 |
| `runs-01/schedule.json` | 全試行の実行順 |
| `runs-01/records.json` | 準備実行も含む各回の時間、RSS、出力検証 |
| `runs-01/summary.json` | 有効な計測だけの中央値、範囲、相対差、個々の値 |
| `runs-01/*/process/` | 各変換の標準出力と標準エラー |
| `runs-01/*/cache-*.json` | 試行前後のモデルと CoreML キャッシュの状態 |
| `combined-summary.json` | 両バッチの全試行を保持した、個人パスを含まない集計 |
| `validation.json` | 全 28 回の PPTX と変換後モデルのハッシュ照合 |

モデル、バイナリ、実資料と OCR 全文は公開リポジトリへ追加しない。
過去の単発計測 31.29 秒、約 1.17 GiB は参考記録として保持し、今回の中央値と区別する。

## ツールの検証

```sh
uv run --python 3.12 python -m unittest discover \
  -s macos-app/scripts/tests -v
```

単体テストは、RSS の単位、プロセスごとの独立したピーク、終了コード、条件別の集計、失敗や欠測の除外、実行順、PPTX の内容変更の検出を扱う。
バッチの集計では、条件の混在、標本の重複、生記録との不一致、個人パスやプロセス一覧の除外も検証する。
Python 3.12.12 と 3.15.2 で、全 10 テストが通過した。
